# 2. Назначение и цели системы

## 2.1. Назначение системы

Приложение предназначено для студентов и сотрудников колледжа и предоставляет единый интерфейс для доступа к учебным сервисам и коммуникации.

Система должна включать:

- расписание;
- успеваемость;
- сводную ведомость;
- посещаемость;
- групповые чаты (по умолчанию создаются профильные, английский, курсовой (каждый год название группы просто будет изменяться), группа преподавателей); 
- личные чаты??
- интеграцию с Redmine (+ уведомления о новых задачах, напоминания о написании комментарии при внесении изменений в задачу (в описании, в статусе и тд);
- уведомления.

---

## 2.2. Цели создания системы

Основные цели:

1. Объединить основные цифровые сервисы колледжа в одном приложении.
2. Упростить коммуникацию между студентами и сотрудниками колледжа.
3. Предоставить студентам удобный доступ к информации об учебном процессе.
4. Предоставить преподавателям удобную возможность работать с посещаемостью.
5. Интегрировать приложение с существующими системами колледжа.

# 3. Пользователи системы

## 3.1. Студент

Студент должен иметь возможность:

- авторизоваться через корпоративную учётную запись;
- просматривать расписание;
- просматривать успеваемость;
- просматривать сводную ведомость;
- просматривать посещаемость;
- пользоваться доступными чатами;
- просматривать информацию о пользователях;
- отправлять медиафайлы;
- закреплять сообщения?
- просматривать участников доступных групп;
- просматривать роли пользователей;
- получать уведомления;
- создавать задачи в Redmine;
- изменять статус задачи в Redmine;
- изменять описание задачи в Redmine;
- писать комментарий к задаче в Redmine;
- переходить по уведомлению из Redmine сразу к задаче (по которой пришло уведомление).
  

---

## 3.2. Преподаватель

Преподаватель должен иметь возможность:

- авторизоваться через корпоративную учётную запись;
- просматривать собственное расписание;
- отмечать посещаемость студентов;
- пользоваться доступными чатами;
- просматривать информацию о пользователях;
- просматривать участников доступных групп;
- просматривать роли пользователей;
- отправлять медиафайлы;
- закреплять сообщения?
- получать уведомления.


---

## 3.3. Администратор?

Администратор должен иметь возможность: 

- авторизоваться через корпоративную учётную запись;
- просматривать список пользователей системы;
- просматривать информацию о пользователях;
- просматривать роли пользователей;
- управлять ролями и правами доступа пользователей;
- просматривать список академических групп;
- управлять доступом пользователей к чатам;
- создавать групповые чаты;
- редактировать информацию о групповых чатах;
- добавлять и удалять участников групповых чатов;
- удалять сообщения;
- отправлять сообщения и медиафайлы;
- отправлять системные уведомления пользователям.

# 4. Функциональные требования

## 4.1. Авторизация

### Требования

Система должна:

- обеспечивать вход через корпоративную учётную запись колледжа;
- проверять введённые пользователем данные;
- определять роль авторизованного пользователя;
- предоставлять функции в соответствии с ролью;
- сохранять авторизацию после закрытия приложения;
- отображать сообщение об ошибке при неверных данных.


---

## 4.2. Расписание

### Для студента

Система должна отображать:

- дату;
- время занятия;
- преподавателя;
- предмет;
- аудиторию.

> **Источник данных:** система колледжа

### Для преподавателя

Система должна отображать персональное расписание преподавателя.

- дату;
- время занятия;
- предмет;
- аудиторию.

> **Источник данных:** система колледжа

---

## 4.3. Успеваемость

Система должна предоставлять студенту информацию о собственной успеваемости.

### Отображаемые данные

- дисциплина;
- оценка;
- дата.

> **Источник данных:** система колледжа

---

## 4.4. Сводная ведомость

Система должна предоставлять студенту доступ к собственной сводной ведомости.

### Отображаемые данные

- оценки, выставленные преподавателями за весь семестр 

> **Источник данных:** система колледжа

---

## 4.5. Посещаемость

### Студент

Студент должен иметь возможность просматривать собственную посещаемость.

### Преподаватель

Преподаватель должен иметь возможность:

1. Открыть своё расписание;
2. Выбрать занятие;
3. Открыть список студентов группы;
4. Указать посещаемость;
5. Сохранить данные.

### Статусы посещения

- присутствовал 
- отсутствовал 
- отсутствовал по уважительной 

> **Куда передаются данные:** в систему колледжа 

---

## 4.6. Чаты

Система должна обеспечивать обмен сообщениями между пользователями.

### Основные возможности

Пользователь должен иметь возможность:

- просматривать доступные чаты;
- открывать чат;
- просматривать историю сообщений;
- отправлять текстовые сообщения;
- отправлять медиафайлы;
- получать сообщения;
- отвечать на сообщение;
- редактировать сообщение?
- удалять сообщение?

### Типы чатов

#### По умолчанию
- чат преподавателей
- чат всех студентов
- чат курса
- чат академической группы
- чат 

#### Вручную
- чат кураторов
- чат с преподавателем по предмету (по просьбе самого преподавателя) 
- чат с командой


### Вложения

- изображения;
- видео;
- документы;
- максимальный размер 15 МГб 

---

## 4.7. Redmine

Приложение должно предусматривать интеграцию с системой Redmine колледжа.

### Возможности пользователя

- просмотр задач
- создание задач
- изменение статуса
- добавление комментариев
- добавление файлов
- назначение исполнителя
- просмотр доступных проектов

  
> **Важно:** конкретный способ технической интеграции определяется после исследования используемой колледжем конфигурации Redmine и доступных API.

---

## 4.8. Уведомления

Система должна поддерживать уведомления о:

- новых сообщениях;
- изменения в расписании 
- новая задача, назначенная на пользователя, в Redmine 
- напоминание о написании комментария после изменения задачи в Redmine 
- напоминание об окончании задачи в день ее завершения в Redmine
